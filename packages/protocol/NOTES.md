# @quietvote/protocol and @quietvote/crypto: implementation notes

Status: reference implementation of QV-16 (suite `qv1-r255-sha2`) after the consistency edit that added QV-ADR-014..024.
Everything below is a deviation, a clarification where the spec is ambiguous, or a known gap. Where QV-16 was ambiguous the
safest reading was taken. Items marked **[X-n]** are spec errata (for the QV-16 owner to fold back).

## What exists

* `packages/crypto`: ristretto255 scalar/point wrappers with strict decoding, identity checks and non-zero sampling; framed
  hashing with a closed label registry (unregistered or wrong-kind labels throw); hedged helpers; exp-ElGamal; Schnorr PoK;
  DLEQ (complaints), CDS 0/1, selection-limit, partial-decryption and spoil-decryption proofs; Feldman/Lagrange; BSGS; share
  cipher (HKDF-SHA-256 + AES-256-GCM via WebCrypto); strict QV-JSON parser and RFC 8785 serialiser; strict Ed25519 (also
  rejects small-order or non-canonical `R`). Existing exports (`sha256`, `sha512`, `ed25519*`) are unchanged.
* `packages/protocol`: manifest validation/hash/roll Merkle; DKG (deal, shares, receive, complain, deterministic adjudication,
  final share, key confirmation, ctx); ballot build/encrypt/sign/verify; Benaloh spoil (three modes); ballot-log analysis
  (window, chain, limit, duplicate code, spoiled set); aggregation; trustee partial decryption (refuses non-recomputed
  aggregates and sub-floor tallies); combination; BSGS; tally record; exact-integer rules; `verifyElection(bundle)`.
* `test-vectors/` (QV-34 envelope), generated by `packages/protocol/test/vecgen` (zero-diff test).

## Spec errata and clarifications

* **[X-1] `verifyElection` is async.** AES-256-GCM share decryption (complaint adjudication) exists only as async WebCrypto, and
  hand-rolling AES is forbidden, so `verifyElection(bundle): Promise<VerificationReport>`; the share-cipher functions are async.
* **[X-2] `selvec` fields.** Registry says "ctx, then one byte per ciphertext"; Appendix A shows `ctx, 01, 00, 00`. Implemented as
  one separate 1-byte field per ciphertext (so `u32(m)` in the frame counts them).
* **[X-3] Record signature scope.** `sig-record` scope is `manifest_hash` for every `dkg-*` record and `dkg-*` marker (including
  `dkg-keyconf`, whose PoK is itself `ctx`-bound) and `ctx` for `election-open`, `election-close` and `tally`. Coordinator records
  (`marker`, `roll-commit`, manifest) carry `sigs[]` and need `m` distinct valid coordinator signatures; the `dkg-final` marker
  carries optional `qmask`/`K` (checked, never trusted).
* **[X-4] Timeliness windows.** commit: before `dkg-r1-open`; dealing: between `r1-open` and `r1-close`; shares: between `r1-close`
  and `r2-close`; complaints: between `r2-close` and `r3-close`; keyconf: between `r3-close` and `dkg-final`. Markers must be
  strictly ordered (`E_DKG_MARKERS`, fatal).
* **[X-5] Equivocation.** Two different timely records of the same type from one trustee disqualify that trustee
  (`E_DKG_EQUIVOCATION`); identical duplicates are ignored. Spec silent.
* **[X-6] Duplicate `A_0` rule** is evaluated only among dealers that already passed commit/PoK checks, and disqualifies all dealers
  in the colliding group. Evaluating against dealers that failed the PoK would let a copier knock out an honest dealer.
* **[X-7] Empty share package.** A dealer with no other dealer in R1 must still publish a (zero-entry) `dkg-shares` record.
* **[X-8] Complaint adjudication** applies whenever the accused published an entry for the accuser, even if the accused is already
  out for another reason (so false accusers are always removed). Complaint `R` is taken from the shares record, not the complaint.
* **[X-9] No `E_` code for aggregate mismatch.** Added `E_AGG_MISMATCH` (F), plus `E_MANIFEST`, `E_MANIFEST_HASH`, `E_MANIFEST_SIG`,
  `E_ROLL`, `E_MARKERS`, `E_DKG_MARKERS`, `E_DKG_EQUIVOCATION`, `E_TRUSTEE_REFUSE`, `E_LOG_ORDER`, `E_TALLY_MISSING` (unused).
* **[X-10] Spoil that matches a cast ballot.** The flagged cast ballot is inadmissible and does *not* advance the voter's
  `supersedes` chain (the voter's next ballot must reference the previous admissible one). `E_SPOILED_CODE_CAST` and
  `E_SPOIL_MISMATCH` are class ALARM: they fail `chk.benaloh.spoiled` but do not flip the verdict (otherwise one voter could
  force a FAIL). `max_spoils_per_voter` excess spoils are ignored.
* **[X-11] Verdict.** PASS iff no F-class finding and a tally was verified; `INCOMPLETE` when everything verifiable passed but no
  tally record exists; otherwise FAIL. Named checks (QV-34 §9.1) can be `fail` while the verdict is PASS (ignored L-class
  ballots, alarms): QV-34's "no mutant passes all checks" holds, QV-16 App. C's "PASS only if no F-class error" also holds.
* **[X-12] Spoil-decryption nonce.** `cp-dec-nonce` has a fixed field list; for `cp-dec-spoil` the ballot code is appended to the
  `oid` field so a failed RNG cannot repeat the nonce across ballots. Registry would need an explicit field.
* **[X-13] `min_counted_ballots`** (QV-ADR-021): effective value = field, else 5 (roll >= 8) or 3; `privacy_ack: true` is required
  whenever the *effective* value is < 10 (so the default also needs it; ADR text only says "values below 10"). Fewer counted
  voters than the floor => `E_BELOW_FLOOR` (F) and trustees refuse. Therefore `V = 0` tallies are rejected, not "empty".
* **[X-14] Manifest additions** (not in §5.6.1): optional contest `winners` (approval default 1, k-of-n default k, single-choice 1),
  `quorum.count` uses field `value`, optional `spoil_trustee_decrypt` (QV-ADR-020: trustee-mode spoils "valid only if the manifest
  enables it"; field name chosen here), optional `min_counted_ballots`/`privacy_ack`. `status-quo` tie-break is yes-no only.
  Bidi controls (U+200E/F, U+202A-E, U+2066-9) in free text are rejected (QV-34 expects it; QV-13 not read).
* **[X-15] Outcome format** (§5.19 leaves `outcome {...}` open): `{kind: passed|rejected|no-quorum|tie|winners, winners?, tied?, reason?}`.
  A yes-no tie exists only when `strict` and `y*den == num*base`; `base == 0` => rejected (`no-base`). Lexicographic tie-break for
  yes-no picks `no`. Multi-winner ties at the cut line: `declare-tie` => `tie`, `lexicographic` => smallest ids.
* **[X-16] Roll root source** (QV-ADR-015): manifest `roll.root/size` optional; when absent a coordinator-signed `roll-commit`
  record `{type:"roll-commit", root, size}` in the log supplies it (QV-18 shape not read; adapt when `board` lands). The roll
  list itself travels in the bundle.
* **[X-17] Trustee `sign_pk`, coordinator and roll keys** must be strict Ed25519 points (canonical, not small order).
* **[X-18] QV-20 vs QV-16.** QV-20 uses `yesno/single/approval/kofn`, a voter-chosen `seq`, `allow_blank`, threshold `base` values
  `yn/cast/eligible`. QV-16 (`yes-no`, `supersedes` chain, `yes+no|counted`) was followed (QV-ADR-016). `eligible` basis and
  `abstain` options are not implemented.
* **[X-19] R-01 vs QV-16 on spoil.** QV-ADR-020 resolved it; implemented as: spoil always signed under `sig-spoil` with
  `reveal_digest`; reveal published only on opt-in (mode `publish`), default `private`, `trustees` only if the manifest enables it.
* **[X-20] Hash-to-scalar of `u32(L)`** etc. use big-endian widths exactly as §5.1; PoK/DLEQ/keyconf nonces are plain CSPRNG
  (OQ-7 unresolved), not hedged.

### Log layer (C3 step 11, QV-05 V4/V7, receipts): `src/logcheck.ts`, `verifyElection(bundle, { log })`

* **[X-21] Origin and `bb.log_id`.** QV-18 REQ-001 says origin = `quietvote/v1/<32-char hex election_id>`, but `board` only accepts
  `quietvote/v1/[a-z2-7]{26}` and `server` derives `quietvote/v1/base32(election_id)`; the base32 form is used. QV-16 never defines
  `bb.log_id`; it is read as `hex(SHA-256(origin))` (as `web` builds it; the tlog-witness monitoring path component) and must match,
  else `E_LOG_BINDING`. (`trustee/src/transcript.ts` uses `quietvote/v1/<log_id>`: inconsistent, flagged for its owner.)
* **[X-22] Entry/record binding.** Log entry 0 is the manifest record; protocol log entry `seq` is log entry `seq`, and the entry body is
  exactly `JCS(record)` (QV-ADR-019); a body-less entry is accepted only if listed in `redactions` and its header digest still matches the
  record. Every log entry must appear in the protocol view and vice versa (else a ballot could be hidden from verification). Header type
  must follow the QV-18 §5.2 mapping (`dkg-open`->`ceremony_start`, other `dkg-*` markers->`notice` (unmapped in QV-18; server choice),
  `dkg-final`->`joint_key`, `tally`->`tally_result`, cast/spoil->`ballot`/`ballot_audit`, ...). Header author: a coordinator key for the
  manifest, markers and `roll-commit` (QV-18 "organizer" = QV-16 coordinator), the trustee `sign_pk` of the record's index, the roll key
  equal to `body.voter`, or the tally's own `sig.key` ("anyone"); unrecognised bodies: coordinator/trustee/caller `extraAuthorKeys`.
  Header signatures are strict Ed25519. Every violation is F (QV-18 REQ-006: server acceptance is never evidence).
* **[X-23] Witness keys.** QV-16 `bb` has only `witness_quorum`; QV-18 REQ-020 requires the manifest to carry the witness list. Added
  optional `bb.witnesses: [{name, pk}]` (Ed25519 tlog-cosignature 0x04 only; distinct names/keys, strict points, not the log key,
  quorum <= list). Trust order: manifest list (hash-pinned), else caller anchors (`log.witnesses`, reported as a caveat); the export's
  own `policy` is never trusted. `witness_quorum > 0` without enough trusted keys is `E_LOG_WITNESS` (F). ML-DSA-44 is not supported.
* **[X-24] Quorum 0.** QV-18 REQ-023 wants a `none_acknowledged` flag that QV-16's closed schema lacks; QV-16 allows 0 with an
  unwitnessed caveat. Followed QV-16/QV-34: `chk.board.witness = not_run`, caveat `NOT WITNESSED`, times reported unwitnessed.
* **[X-25] Gating and witnessed times.** election-open needs a quorum-witnessed head of size in `[max(seq dkg-final, seq roll-commit)+1,
  seq(open)]`; with a tally record, a witnessed head of size in `[seq(close), seq(tally)]` (QV-18 §9.4) else F; unwitnessed tally/latest head
  is a caveat. QV-16 §5.14.3 times use the *earliest* quorum-witnessed head covering the marker (size > seq), and at least `k` of its
  valid cosignature timestamps must satisfy the bound (open: `>= voting_open - skew`; close: within `voting_close +/- skew`), else
  `E_TIME_WINDOW` (F, QV-05 V7); a missing covering head is F only once a tally exists. Witness timestamps only bound append time from
  above, so the "not early" checks are weak against an operator who delays cosigning (inherent; stated).
* **[X-26] Evidence rule.** Only log-signed notes are evidence. Externally observed heads (`log.observed`: pins, gossip, witness
  monitoring) that do not parse/verify are warnings; a log-signed head larger than the log is `E_LOG_ROLLBACK`, a different prefix root
  `E_LOG_FORK` (both F). Two log-signed roots for one size in the export are `E_LOG_FORK`; a missing full-size head is `E_LOG_CHECKPOINT`.
* **[X-27] Receipts.** A receipt whose promise verifies under `bb.log_pk` but is not honoured (seq beyond the log, another leaf at seq,
  receipt head not a prefix) is F. A malformed or non-log-signed receipt is class I: `chk.receipts.sample` fails, the verdict does not.
* **[X-28] Clash.** The receipt holder's key must be the entry's author and the envelope's `voter` (and the recorded code must match when
  given); two claimants for one entry are flagged. These are ALARM: anyone can fetch any receipt, so a claim alone proves nothing to a
  third party (same reasoning as X-10). `verifyReceiptChain` (voter side) fails closed on the same mismatch.
* **[X-29] Witness monotonicity.** A witness whose cosignature timestamps decrease as tree size grows is excluded from quorum counting
  with an ALARM (QV-18 §9.6 `witness_conflict` is a witness fault; one witness must not force a FAIL, nor help reach quorum).
* **[X-30] API/codes.** `verifyElection(bundle, {log})`: `log.board` is the `board.bundleToJson` export; absent => C3 checks `not_run`
  (unchanged). New F-family codes `E_LOG_FORMAT/BINDING/CHECKPOINT/FORK/ROLLBACK/WITNESS/RECEIPT` and ALARM `E_LOG_RECEIPT_CLASH`
  (QV-16 §8 `E_LOG_*`). `verifyReceiptChain` (QV-05 §4.3): promise + inclusion + own header/voter + consistency to a later log-signed head;
  when `witness_quorum > 0` the later head must carry the quorum, else `E_LOG_WITNESS`.

### Notices and control entries (QV-18 §5.2 `notice`, §9.4 waiver, QV-ADR-022): `src/logcheck.ts`

* **[X-31] Record shape.** No spec defines the body of a waiver or extension in suite v1 (QV-18 §5.2 gives only `{code, text}` with codes
  `witness_waiver`, `extension`, `info`; QV-16 §5.14.3 says the extension record is "not defined in suite v1", OQ-9 "none in v1").
  The verifier therefore uses the record `packages/server` already writes for control entries: `{body: {proto, type: "control",
  action, reason?}, sigs}` (closed schema), coordinator multi-signed over `sig-record(manifest_hash, "control", body)` (X-3 convention,
  same scope as the server). Recognised actions and their entry type: `pause`, `resume`, `invalidate`, `security-notice`,
  `witness-waiver`, `extension` -> `notice`; `audit-close` -> `audit_close`; `cancel` -> `election_cancel`; `abort` -> `ceremony_abort`.
  `witness-waiver`/`extension` are the QV-18 codes spelled like the server's actions (`security-notice` for QV-ADR-022
  `security_notice`); the server does not emit them today (its `CONTROL_ACTIONS` rejects them). QV-18 `info`/`redaction` notices
  have no record shape anywhere and are therefore unknown kinds (fail closed, X-33). **Owner decision needed** on the record shape,
  the naming and the signature scope (manifest hash vs ctx); vectors use the reading above.
* **[X-32] Notices never relax a gate.** Every witness gate (QV-18 §9.4, §13 step 6; X-25) and the QV-16 §5.14.3 time window read only
  the hash-pinned manifest (`witness_quorum`, `bb.witnesses`, `voting_open/close`, `clock_skew_s`) and the tree heads; nothing reads a
  notice. A waiver cannot lower `k`, replace the witness set or unblock a gate (QV-18 REQ-020: witnessed status from the manifest
  only). QV-18 §9.4 / REQ-051 let an organizer waiver unblock the *server's* phase transition and QV-18 REQ-052 asks verifiers to
  "surface it prominently": done as a `WITNESS WAIVER` caveat; the gate finding stays F (with a "never relaxes" note). This is
  stricter than `board.verifyLog`, which downgrades a waived gate to a warning via `isWitnessWaiver`. Extensions, pause and resume
  never move `voting_close` (QV-16 §5.14.3 has no such input; QV-03 §9 halt credit and QV-03 §5.5 extensions are not applied);
  they are reported as caveats. Because the closed schema admits only `action` and `reason`, a notice cannot even carry a quorum,
  witness list or time (`E_LOG_FORMAT`).
* **[X-33] Authority and fail-closed rules** (all F, `chk.board.append_only`): the entry header author must be a manifest coordinator
  key (QV-18 REQ-052 "signed by the organizer"; QV-ADR-022 / P12-2: the operator may only hold or notify, so caller
  `extraAuthorKeys` never authorise a control entry) **and** the record needs >= `coordinator.m` distinct valid coordinator
  signatures over this election's manifest hash (so a waiver replayed from another election fails) -> `E_LOG_BINDING`; a control
  record in the wrong entry type -> `E_LOG_BINDING`; malformed record (unknown/extra fields) -> `E_LOG_FORMAT`; unknown action (incl.
  prototype names, case variants, QV-18's underscore spelling) -> `E_LOG_BINDING`; a `notice` entry whose body is neither a DKG
  round marker (X-22) nor a control record -> `E_LOG_BINDING`. QV-03 §5.5 / QV-ADR-022 give extension authority to k stewards;
  stewards are not in the QV-16 manifest, so the coordinator m-of-k stands in (ambiguity, owner to confirm).
* **[X-34] Retroactive extension.** An authenticated `extension` sequenced after `election-close` is `E_TIME_WINDOW` (F,
  `chk.time.window` fail): QV-03 §5.5 allows extensions only before close, and the close seq is the cutoff (QV-ADR-P18-3). It is F
  even with `witness_quorum = 0`. Wall-clock "before close_at" is not checked (no witnessed time for the notice itself); QV-03
  `max_times`/`max_hours`/`allowed_if` caps are not checked because no extension is ever applied. Not interpreted: the effect of
  `invalidate`, `cancel`, `abort` on the verdict (reported as caveats only; QV-05 V13 is still not implemented).
* **Protocol-layer view of control records.** They are not QV-16 suite v1 records, so `verify.ts` reports them as `E_VERSION
  unknown record type` (class L) and fails `chk.encoding.canonical`; the log-layer vectors with notices record that (expected check
  maps include `chk.encoding.canonical: fail`). If `verify.ts` later dispatches `control` records, those vector expectations change
  (regenerate; set is `candidate`).

### Log-layer test vectors (QV-34): `test-vectors/v1/elections/log-layer-4v/`

* One vector set, operation `log.verify_election` (the full verifier with QV-18 log evidence; QV-34 §10.2 file-based inputs): 48 vectors
  over an honest 4-voter election (revote, tally; witnesses w1..w3, k = 2), an adversarial view of it (revote dropped and re-signed),
  and 11 notice scenarios derived by inserting a control record. Input: `{bundle: {path}, board: {path, replace?}, receipts?, observed?,
  witnesses?}`; `replace` shallow-replaces top-level fields of the export (mostly `checkpoints`). Expect: positive
  `{ok: true, output: {verdict, checks}}` (no log-layer finding, verdict PASS); negative `{ok: false, error, failed_checks}` (QV-34 §6.3
  form) with the verdict as a `verdict:` tag (ALARM / class I receipt cases keep PASS). `surfaces:` tags name caveats that must appear.
* They live under `elections/` because they are election-level verifier vectors; the generic per-operation runners
  (`vectors.test.ts`, `qv vectors check`) skip `elections/`, and `loglayer.test.ts` runs this set. The directory follows the
  `elections/<name>/` convention (`bundle.json` + `expected-report.json` for the honest bundle verified without log evidence), which
  `qv vectors check` relies on. Adding them changed only `MANIFEST.json` (new entries +
  root); every existing vector file is byte-identical.

## Mismatches the consistency editor asked to list

* `KeyId` (QV-09) is undefined in QV-16/QV-30; this code identifies keys by 32-byte Ed25519 public key hex everywhere.
* QV-05 mapping says V13 (steward/operator authorisation, control entries of QV-ADR-022) has no Appendix C step: not implemented
  or verified here (no `pause/resume/invalidate` entries are parsed; they would be reported as unknown record types, class L).
* ~~`election_open` is only a marker~~ RESOLVED, see **[X-40]** below.
* QV-ADR-019 (log entries as exact canonical bytes with base64url transport) is a `board`/`server` concern; the verifier takes
  parsed JSON (strict parse available via `verifyElectionText`) and re-canonicalises bodies.
* QV-ADR-024 vendoring of `@noble/*` not done (dependency pinned by lockfile only); `packages/protocol/package.json` does not list
  `@quietvote/crypto` (workspace symlink resolves it; adding it needs a lockfile refresh).

## !! VERSION-IMPACTING CHANGE: election-open binding (QV-ADR-015), X-40

* **[X-40] `election-open` now carries `(manifest_hash, joint_key_seq, roll_commit_seq)`** and a `roll-commit` record is mandatory
  before it (docs/18 §5 sequence: `... joint_key, roll_commit, election_open`). The marker body gains three fields
  (`manifest_hash` hex32, `joint_key_seq`, `roll_commit_seq` = log `seq` values), signed under scope `ctx` as before; builder
  `electionOpenBody()` in `records.ts`. Schema: optional on `marker`, but **required on `election-open`, forbidden on every other
  marker** (`E_SCHEMA`, class L). Verifier (`verify.ts`), fail closed with `E_MARKERS` (F), `chk.time.window` = fail:
  missing field; `manifest_hash` != manifest hash; either ref >= the open's own seq (forward/self); `joint_key_seq` != seq of the
  accepted `dkg-final` marker; `roll_commit_seq` not a validly coordinator-signed `roll-commit` record; or the referenced
  roll-commit root/size differs from the supplied roll. (No new error code invented: reuses `E_MARKERS`; `E_ROLL` would also be defensible for the last case.)
  An election with no `roll-commit` record can no longer reach PASS even if the manifest embeds `roll.root` (static-roll mode
  still allowed for the manifest, but the log must carry the commit that the open binds).
* **Vector impact (deliberate, existing bytes changed):** the sim (`test/helpers/sim.ts`) now emits `roll-commit` then the bound
  `election-open`, so every election bundle changed (`elections/tiny-yesno-3v`, `small-approval-20v`, `log-layer-4v`), every
  mutation derived from them, and the canary; all seq numbers after `dkg-final` shifted by one. Primitive vectors are
  byte-identical. Added by addition: 8 mutants `mutations/open-*` (roll ref forward/absent/wrong-record/nonexistent, joint-key
  ref forward/mismatch, all fields absent, manifest_hash mismatch). Regenerated with
  `node --experimental-strip-types packages/protocol/test/vecgen/write.ts`; the zero-diff regen test is green against the new bytes.
* **Downstream consumers must update:** `packages/{trustee,board,cli}` and `packages/verifier` and `verifier-py` (all outside this
  task) build/parse `election-open` without these fields; they will be rejected (`E_MARKERS`) by this verifier until updated.
  `verifier-py` (not edited) rejects the new open marker with `E_SCHEMA`.
* **Server** (`election.ts`): `election_open` is rejected (422 `E_MARKERS`) unless all three refs are present and equal the server's
  own `manifest_hash`, `dkg-final` entry seq and `roll_commit` entry seq (so absent/forward/mismatched refs never enter the log).
  The server does not author the open (the coordinator signs it); `World.open()` in the server tests builds the bound marker.
* **Record sequence (docs/16 vs docs/18) and `tally_aggregate`:** docs/18 lists `roll_commit` before `election_open` (now emitted
  and required). docs/18 also lists a `tally_aggregate` entry before `tally_result`, but QV-16 defines **no** such record: the
  verifier recomputes the aggregate from the counted ballots, and the `tally` record carries `counted_root` and the aggregate
  proof inputs. AMBIGUOUS, so protocol deliberately does NOT emit a `tally-aggregate` record (it would be an unknown type, class L,
  in every verifier, and QV-16 has no body for it). The server's own `tally-aggregate` record (`server/src/records.ts`) stays a
  board-level derived record; if QV-16 later defines it, add it between `election-close` and `tally`.

## Known gaps

* Log layer (X-21..X-30) runs only when the caller passes `{log}`; `packages/verifier` still composes `board.verifyLog` itself and does
  not pass log evidence to `verifyElection` yet (not changed here). Control/notice entries are authenticated and reported but never
  applied (X-31..X-34); their governance effect (QV-05 V13: pause/resume windows, invalidate/cancel verdicts) is not implemented.
* Secret types (`SecretScalar` etc., QV-30 S2), wiping, and lint rules (QV-30 §5.2) not done; scalars are plain `bigint`.
* Constant-time claims are those of `@noble/*` only.
* Test vectors: `status: candidate`; no independent second implementation; MANIFEST unsigned; external-standard sets contain only
  a handful of values re-derived by computation (not verbatim imports with source hashes); RNG is a SHA-512 stream, not `vecrng-v1`;
  mutants derive from `tiny-yesno-3v`, not the 20-voter election; no `scale/` set, no `edge-ties-quorum` election, no JSON Schema
  files for ops (only registries).
* Mutation of `n` > 32 / roll > 2^20 limits are enforced by schema bounds but not fuzzed.
* Performance: ~35 ms per ciphertext for build + two verifications in JS; the 50-voter end-to-end test takes ~25 s.

## Spoil shares and private audit (audit/QA wave 1)
* `src/spoilshare.ts`: `SpoilShareBody`, `spoilShareRecordSchema` and `collectSpoilShares(m, ctx, code, records)` (QV-ADR-020 trustees mode).
  The record is signed by the trustee `sign_pk` under scope = ctx, is NOT a board record (packets only) and reaches verifiers via
  `tally.spoiled[].shares`, which `verifyElection` already checks. The collector rejects wrong ctx/code/index, bad signature, duplicates
  (first wins), duplicate share keys and undecodable points; DLEQ proofs are checked by `decryptSpoiled`, not by the collector.
  `trustee` still carries its own identical schema/type (same wire format); switching it to this export is a follow-up.
* `auditSpoil(p, roll, env, reveal)` (ballot.ts): voter-side private audit = envelope verifies + reveal reproduces the ballot +
  `reveal_digest` commits to the reveal (zero digest = trustee mode, commits to nothing). New vector set
  `protocol/benaloh/private-audit.json` (operation `benaloh.private_audit`, QV-10/QV-34), runners in `vectors.test.ts` and `qv vectors check`.
* Unaudited; not for real elections.
* **TR-01 (trustee audit)**: `analyzeBallotLog` now returns `castAlphas` (every `a` of every cast envelope in the log, valid or not;
  `collectAlphas`). `verifyElection` fails `chk.benaloh.spoiled` with ALARM `E_SPOILED_CODE_CAST` when a trustees-mode spoil in the tally shares
  any `a` with a cast envelope: spoils are not chain-checked and proofs bind only (ctx, voter), so a voter could re-wrap a cast ballot's
  ciphertexts under a new code (`supersedes`) and have trustees decrypt it. Test: `tally.test.ts` (fails without the check).
* **CP-01 (crypto-protocol audit)**: the TR-01 rule is enforced in `analyzeBallotLog` itself (any mode, either order), not only for tally-listed
  trustees-mode spoils. **CP-03**: closed schemas use `Object.hasOwn`. **CP-04**: `ed25519IsStrictPoint` (crypto) now also requires a
  torsion-free point (mixed-order roll/author keys and signature R values are rejected). See `docs/audit/crypto-protocol.md`.

## Second-wave triage (crypto-protocol audit, 2026-10-21)
Details and evidence: `docs/audit/crypto-protocol.md` § "Second-wave triage". Regression tests: `protocol/test/second-wave.test.ts`,
`crypto/test/second-wave.test.ts` (every test failed before its fix). Behaviour changes:
* `verifyElection`: a later tally record whose body differs from the first is F `E_RESULT` (identical repeats stay L) (P3).
  `chk.tally.decrypt` is `pass` only after share verification + combination actually ran; it stays `not_run` below the floor or when
  the aggregate check failed, and a `chk.result.rules` failure (e.g. `E_BELOW_FLOOR`) is no longer overwritten with `not_run` (P7, TSV-03;
  vectors regenerated: only the affected `chk.tally.decrypt` statuses change). `tally.decrypters` must equal the recomputed `T_valid`
  (F `E_DEC_PROOF`, `chk.tally.decrypt` fail) (P11); `buildTally` now emits `T_valid`. A keyconf only settles trustee j when it verifies,
  so an invalid earlier keyconf no longer shadows a later valid one (P9, §5.7.8).
* `analyzeBallotLog`: a voter-signed spoil whose attached `reveal` fails `reveal_digest` is still registered as spoiled (ALARM
  `E_SPOIL_MISMATCH`, benaloh fail), so the same code cast later is excluded (P4, REQ-015).
* `trusteeDecryptTally` refuses a counted list with a repeated voter or ballot code (`E_TRUSTEE_REFUSE`) (P2: floor padding).
* `validateManifest`: trustee and witness names get the NFC / bidi-control check (P6).
* crypto (no NOTES of its own): `encryptShare` rejects identity `E_j`; `elgamalEncrypt` requires `0 < r < l`; `canonicalize` rejects
  non-plain objects (Map, typed arrays, Date), non-NFC strings/keys and lone-surrogate keys; `limitVerify` returns false for non-u32 `L`;
  `lagrangeAtZero`/`feldmanVerifyShare` reject index 0; `dhVerify` rejects identity `Ej`/`R`/`S`, `decVerify` identity `Yj`;
  `BUNDLE_MAX_LOGN` 22 -> 20 (bundles sealed at 21/22 can no longer be opened; none in this repo) and `openWithPassphrase` takes an
  optional lower `maxLogN` cap (trustee does not pass it yet).
* Open / design (no code change): P1 (PASS without `opts.log`, TSV-05), P10 (duplicate election markers first-wins, L), C3 (unhedged
  DKG/complaint nonces, OQ-7), CP-02/C2, C11 (test RNGs exported from the index; other packages' tests import them).
* Second-wave vector change: the canary `expected-report.json` now has `chk.tally.decrypt: not_run` (was `pass`): the check is `pass` only after decryption actually ran (P7/TSV-03); the canary's wrong aggregate stops the pipeline earlier.
