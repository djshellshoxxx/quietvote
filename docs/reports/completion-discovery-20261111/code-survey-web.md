## 3. Voter journey as implemented

Format `/e/ID#inv=TOKEN[&read=KEY][&board=URL]` parsed by parseFragment (flow/invite.ts:147-172). token must be 16 bytes b64url; read key regex 16-64 chars. `board=` is parsed and validated (invite.ts:160-168, :175) but **never used by app.ts** (only `frag.readKey`, `frag.token` used: app.ts:373-374, 388). `apiBase` is never set by main.ts (main.ts:21-28), so API is always same-origin. The fragment is never stripped from the address bar/history after use (only replaceState call is language switch, app.ts:860).
2. **Key generation/storage**. keyView app.ts:438-526. Options: create (passphrase policy check app.ts:510, generator app.ts:487), import `.qvkey` (:503), restore from paper recovery code (:497), CLI hint (:492, text only). `createKey` (flow/onboarding.ts:34): 32-byte seed from `systemRng`, wrapped with Argon2id (default m=65536,t=3,p=1; floor 19456/2/1; ceiling 262144/10/4; key/keystore.ts:15-17) + AES-256-GCM, stored in IndexedDB db `quietvote-v1`, store `keys`, slot `voter:<electionId>` (storage.ts:97-98, onboarding.ts:16). Only the wrapped container is persisted (keystore.ts:1). **Private key is encrypted at rest** by passphrase. Unlock -> seed unwrapped, converted to non-extractable WebCrypto Ed25519 key if supported, else seed held in a closure (key/signer.ts:218-264, 240); seed buffer wiped. Signers kept in an in-memory Map per election (app.ts:82). Auto-lock: idle 10 min, hidden >2 min, 2-min warning (key/lock.ts:3-5; app.ts:95-112).
3. **Backup/restore**. After create/unlock, `Download key file` (.qvkey = wrapped container, app.ts:458) and `Show recovery code` (re-asks passphrase, shows seed as Crockford code, app.ts:459). ## 6. Security posture as coded
- **CSP** (site.ts:63-71): `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' + build-time allowlisted origins; worker-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; object-src 'none'; require-trusted-types-for 'script'; trusted-types qv-default; upgrade-insecure-requests`; header adds `frame-ancestors 'none'` and `report-uri /csp-report`. Meta copy omits frame-ancestors/report-uri (meta cannot carry them). `_headers` file adds COOP same-origin, COEP require-corp, CORP same-origin, Referrer-Policy no-referrer, HSTS, nosniff, Permissions-Policy (site.ts:78-85). Whether the server actually serves `_headers` or its own set: UNVERIFIED (server code not read). Connect origins validated against an origin regex (site.ts:56-60).
- **innerHTML / insertAdjacentHTML / eval / new Function / document.write / srcdoc**: **none in src, static or e2e** (grep). ## 8. Gaps and SUSPECTED defects (none executed; ordered by voter-harm priority)

1. **SUSPECTED - ballot recorded but UI shows no receipt on a post-submit integrity alarm.** In `castOnce` the POST has already succeeded when `verifyAppendResult`/`checkAgainstPin` throw `BoardIntegrityError` (ballot-controller.ts:152-155). The catch (:176-195) sets `unknown=false`, outcome `PENDING_UNCONFIRMED`, dispatches CAST_FAILED with `retryCast=false`; the receipt is neither stored (:163-171 not reached) nor offered. The failed screen (app.ts:603) shows only the E-BOARD-* box and a "New seal" button; `NEW_SEAL` is a no-op for this state (ballot-machine.ts:106 requires `spoiled.includes(code)`), so the button does nothing visible. A voter may not learn the ballot may be recorded and has no receipt to check later.
2. **SUSPECTED - unknown-delivery retry state is in-memory only.** `pending` signed entry lives in the controller (ballot-controller.ts:54,145-151). Reload, navigating away or opening /vote again builds a fresh controller (app.ts:535) with no memory of the unconfirmed send; nothing is persisted (no storage write before response). If the first send actually landed, the voter sees a clean ballot form with no "you may have already voted" warning; in max_per_voter=1 elections the second attempt ends as E-VOT-ONEBALLOT after sealing a new ballot; in revote elections it silently creates a second ballot superseding the first.
3. **SUSPECTED - no "already voted" pre-check.** voteView computes `supersedes` from the log (app.ts:534) but does not block or warn when it is non-zero and `max_per_voter === 1`; the form is shown and the refusal arrives only after seal+send (errors.ts:299, `REVOTE_LIMIT`).
4. **SUSPECTED - misleading rejection copy.** `E-VOT-REJECTED-PROOF` says "Nothing was recorded. Reload this page and try again" (en.ts:433) and is mapped for ENTRY_INVALID, MALFORMED_ENTRY and VALIDATION_FAILED (errors.ts:300-302); only reasons E_SUPERSEDES/SUPERSEDED map elsewhere. Unmapped 4xx codes fall to `E-GEN-UNKNOWN` with outcome REJECTED ("Not accepted", app.ts:595) even though the client cannot distinguish all definite refusals from other 4xx (e.g. 409 STATE_CONFLICT). Treating every non-5xx/non-429 status as definite non-recording is an assumption (ballot-controller.ts:177-181).
5. **SUSPECTED - 429 treated as unknown delivery.** `(e.status===429 && code!=='REVOTE_LIMIT')` is classed as unknown (ballot-controller.ts:178) though a rate-limit rejection is a definite non-record; voter sees "We're not sure your ballot arrived" (en.ts:420) after 4 retries (client.ts:201). Conservative but possibly confusing; DUPLICATE_IGNORED and SUPERSEDED outcomes are effectively unreachable: `E-VOT-DUP` is never returned by `uxCodeFor` (errors.ts:292-310; grep) and `SUPERSEDED` is never dispatched (grep ballot-controller/ballot-machine), though titles exist (app.ts:595).
6. **SUSPECTED - draft selections lost without warning.** Selections exist only in the DOM and in controller memory until "Review" (app.ts:562); the auto-lock/visibility handler redraws a "locked" page for `selecting` state (app.ts:539) discarding the user's choices; `route()` also drops them. No confirmation/warning before auto-lock destroys unsent choices (warning text only covers idle lock, app.ts:102).
7. **SUSPECTED - spoil (test) posting default-on reveals voter activity and swallows failure.** `post-chk` default checked (app.ts:579); the `ballot_audit` entry is signed by the voter key and appended to the public log (ballot-controller.ts:223-229), linking voter key to having tested; failure silently becomes "not posted" (:230-232). Also the downloadable `qv-audit.json` contains the opened plaintext selections and randomness of the test ballot (app.ts:591, audit.ts auditText); if a voter tests with their real choices and shares it, they have disclosed their real choice (by design for the test, but copy risk).
8. **SUSPECTED - invite token and read key persist in URL.** Fragment `#inv=` is never removed after registration (only replaceState at app.ts:860); stays in history/bookmarks/open tab. Tab links append the hash only when a token exists (app.ts:388), so a read-key-only link (`#read=`) is dropped from internal links and from reload. Token is 128-bit and only the hash is sent (when the contract is fixed), so risk is local-device exposure.
9. **SUSPECTED - B3-01 mismatch is a hard blocker for any real voter.** See 3.4 call sites. Web sends `invite_code = b64u(SHA-256(token))` and a PoP over a different byte layout; the server hashes the code string it issued and verifies a different PoP message (app.ts:562-563). Real registration would fail (422 INVITE_EXPIRED or 401 BAD_SIGNATURE, per server order the PoP check runs first -> 401). All web tests pass only because FakeBoard always returns 403 (fake-board.ts:168-176). Additionally the UI shows `E-GEN`/mapped error for `BAD_SIGNATURE` (not in uxCodeFor switch, errors.ts:294-309 -> E-GEN-UNKNOWN).
10. **SUSPECTED - pending registrations never resolved in UI.** `status:'pending'` is reported as "registered... organizer will add it" (app.ts:464,474); `ApiClient.voter()` is never called, so the voter gets no signal about approval; no organizer approve UI exists.
11. **SUSPECTED - organizer flow cannot complete.** No organizer key creation UI (app.ts:781 reads only), no roll-commit, open, close, tally or export (section 4). `/e/:id/admin` is copy-only (app.ts:421). Copy promises organizer open/close signing and "Download everything" (en.ts:382,387) that the code does not provide.
12. **SUSPECTED - overview deadline display ignores the viewer's time zone.** `formatDeadline(iso, tz, tz, locale)` is called with the browser zone for both election and viewer arguments (app.ts:395), so `electionTime` is rendered in the viewer zone even though the label may imply the election's zone; whether the manifest carries a zone: UNVERIFIED.
13. **SUSPECTED - hard-coded organizer parameters mislead the organizer.** k-of-n `k:1`, `maxBallots:8`, `quorumCount:0` are fixed (app.ts:841-842); the preview also uses a placeholder coordinator key and the pasted log key is only used for the preview (app.ts:843 vs publish.ts:147-157). Organizer sees a "freeze" confirmation for parameters they cannot edit.
14. **SUSPECTED - accessibility and "shared device" gaps.** `sharedDevice`, `rememberReceipts`, `rulesSeen` settings have no UI (grep) although the copy `qv.device.shared` is shown (app.ts:521), so a user on a shared device cannot opt out of receipt retention except by "Clear this device" (app.ts:523). Language picker never renders today (only English offered). No automated a11y coverage of voting/key/organizer screens (a11y.ts:5-6).
15. **SUSPECTED - double-submission across tabs/devices is not guarded client-side.** `castInFlight` and reducer states protect one controller only (ballot-controller.ts:55,128-135). Two tabs each seal independent ballots (different randomness) for the same voter key; the second is either rejected (one-ballot) or becomes a supersede on the log.
