# Deterministic lockfile SBOM — 2026-11-27

## Scope and contract

This implements the bounded generator and CI stdout acceptance in
[process task T4](inventory-20261111/process.tasks.md#t4-sbom-generator).
[QV-19 §10.4 and REQ-028](../19-client-supply-chain.md) specify CycloneDX 1.6
and a component list equal to the lockfile production closure. The generator
therefore includes every declared workspace and its production dependencies by
default; `--include-dev` explicitly inventories all external lockfile records as
well. It uses Node built-ins and adds no dependency or third-party action.

```sh
node scripts/sbom.mjs --stdout
node scripts/sbom.mjs --stdout --include-dev
node scripts/sbom.mjs --stdout --lockfile path/to/package-lock.json
node --test scripts/sbom.test.mjs
```

The CI change emits the production JSON after lockfile lint and before dependency
installation. The existing `tools:test` step discovers the new tests. The existing
SHA-pinned checkout and Node setup actions are unchanged.

## Inventory behavior

- The eight workspace components are `@quietvote/board`, `cli`, `crypto`,
  `protocol`, `server`, `trustee`, `verifier`, and `web`. Their recorded versions
  are preserved, including the current `0.0.0` development versions. Each local
  component appears once; its `node_modules` link is resolved to that component
  and is not represented as an external tarball.
- The current production closure has **10 components**: the eight workspaces and
  `@noble/curves@2.4.0` plus `@noble/hashes@2.4.0`. The explicit development mode
  has **43 components**: the eight workspaces and all 35 external records,
  including optional platform packages. This is not a host-specific installed
  package inventory.
- Dependency edges resolve the nearest recorded installation location, including
  nested installations and workspace links. Required dependencies missing from
  the lockfile refuse generation; absent optional dependencies and optional peers
  are allowed. Cycles terminate without duplicating components.
- External names, exact versions, recorded distribution URLs and declared licenses
  are preserved. Licenses are copied as named declarations; the generator does
  not infer legal approval or normalize declarations into verified SPDX IDs.
- Every external entry is validated before production filtering, including
  development-only entries. A missing integrity field, unsupported algorithm,
  malformed or noncanonical base64, wrong digest length, conflicting hashes for
  one algorithm, unsupported source or nonliteral version causes a nonzero exit
  with no partial JSON. Registry sources follow the existing npm-registry-only
  repository policy. Workspace links are separately checked against local
  workspace metadata and cannot substitute for an external integrity record.
- SHA-256, SHA-384 and SHA-512 SRI digest bytes become the corresponding
  CycloneDX hexadecimal hashes. They identify **recorded registry tarballs**;
  this operation does not fetch packages or verify installed contents. The
  separate existing vendor checks retain that responsibility for vendored crypto.
- Component and edge ordering is canonical and references derive from lockfile
  paths. No timestamp, random serial number, filesystem absolute path or local
  environment value enters the JSON. Generation reads only the supplied lockfile.

The supported input is npm lockfile v2/v3 using this repository's `packages/*`
layout or explicit `packages/<name>` workspace paths. Other layouts refuse rather
than being guessed. Workspace completeness is relative to the lockfile: if both
a workspace record and its link disappear beneath a wildcard declaration, the
generator cannot discover a missing on-disk workspace without another input. The
actual-repository regression independently requires the eight expected names.
This is not a general npm installation or semver solver.

## Limits and remaining release work

This closes the generator/stdout slice of T4. It does not close QV-19-REQ-028's
per-release publication, signing, attestation or manifest linkage. No SPDX
export, comparison with a prior release, vulnerability clearance, artifact build
provenance, legal approval or release readiness is asserted. Those release
requirements remain separate work. Local workspace source hashes are not
invented from the package version or the link target.

Primary format references:

- [CycloneDX 1.6 JSON reference](https://cyclonedx.org/docs/1.6/json/): component
  scope, named licenses, hashes and dependency references.
- [npm package-lock.json reference](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/):
  installed-location records, workspace links, registry artifact integrity and
  development/optional flags.
